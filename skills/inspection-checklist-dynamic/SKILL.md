# 检查项动态生成（inspection-checklist-dynamic）

## 这个技能解决什么

把「这次巡店到底查哪几项」从**固定清单**改成**按本次输入动态决定**，并且必须能回答评委的那句追问：
**"去掉 AI 用规则引擎能不能做？"** —— 答案要靠「本次为什么查这几项」的理由列表落地，不能靠清单本身。

## 什么时候用

- 店长端提交了一次自查（照片 + 一句话），要决定这次查哪几项；
- 督导端要看某张检查单"当初为什么查这几项"；
- 有人想往代码里写死一张检查项表时 —— 加载本技能，改成调模型。

**不要**用在本单之外（例如把这张检查项表当成"标准表单"发给客户），也不要用它生成"勾选表"（本单店长端不做勾选表）。

## 判定维度库（**参考**，不是清单）

下面 6 个维度是**没有注入客户标准时**的**内置兜底**参考项，模型可以增删、可以只选其中一部分、也可以按本次输入提出维度外的检查项：

1. 人员与卫生（工服、健康证、手部清洁）
2. 食材与半成品（生熟分开、覆盖、温度、效期）
3. 台面与设备（操作台、灶台、冰柜、清洁度）
4. 地面与通道（积水、油污、杂物堆放、通道占用）
5. 三防设施（防蝇防鼠防尘、垃圾与垃圾桶）
6. 标识与留样（效期标签、留样记录、公示信息）

### 客户/总部的检查标准是**可注入**的（`standards.json`）

参考维度**不写死在代码里**：客户把自己的门店检查标准放进文件就生效，**不用改代码、不用重启**。

- 位置（按优先级）：① 客户可写区 `<$DSH_HOME>/gaia-inspection/standards.json`（推荐）→ ② 插件目录 `gaia-inspection-core/standards.json` → ③ 内置上面那 6 条兜底。
- 形状：`{ "version": "示例连锁·门店自查标准 v1", "dimensions": [{ "name": "人员与卫生", "items": ["工服","健康证"] }] }`（`dimensions` 也接受纯字符串数组）。
- **统一还是分业态，由客户决定**：不写 `byFormat` 就是全公司统一一份；写了 `byFormat` 就按门店档案里的业态取专项
  （`{ "byFormat": { "快餐档口": { "version": "快餐档口专项 v3", "dimensions": [...] }, "正餐堂食": [...] } }`）。
  匹配是"精确 → 宽松包含"（键写 `快餐` 也能命中业态 `快餐档口`）；某业态没专项 → 退回**通用** `dimensions`；文件都没有 → 内置。
- 读不到 / JSON 坏了 → 退回内置 6 条并把原因写在返回的 `data.standards.error` 里（不抛错、不假装读到）。Windows 的 UTF-8 BOM 会被自动剥掉。
- 每次调用的日志摘要都写明本次用的是哪套标准（分业态时会写"按业态专项·快餐档口"），可用 `inspection_model_calls` 逐条核对。
- 随包带模板 `gaia-inspection-core/standards.example.json`（不会被读取）。

**答辩口径（背下来）**：「检查标准是可注入的：总部把自己门店的检查标准给进来，模型以它作为参考维度，同时保留按本次照片与说明动态增删的能力——所以它不会退化成一张固定的勾选表。这也是为什么去掉 AI、换规则引擎做不到：规则引擎只能对着注入的标准逐条勾，无法在标准之外提出新检查项并说明理由。」

**可增删规则**：
- 本次输入（店长说明 / 照片）直接指向某个维度 → 该维度权重调高（4-5）；
- 注入标准里与本次输入和业态都无关的维度 → **删掉**，不要为了"对齐标准"凑数量（标准是参考，不是逐条勾选）；
- 标准里没写、但本次照片或说明里确实出现的问题 → **必须提出**，并在 `why` 里说明理由；
- 业态相关但本次没线索的维度 → 可保留、权重 3 左右，也可删；
- 信息不足时（例如没有照片、说明只有几个字）→ 在 `reasons` 里如实写"信息不足"，**不要编线索**。

## 执行步骤

1. **收集本次输入**（三样）：
   - 门店：`storeId` / `storeName` / `storeType`（快餐档口 / 正餐堂食）；
   - 店长说明：本次那一句话原文；
   - 照片线索：只给"机器可见的原始线索"（例如"地面有深色散落物"），**不要**把判断结论当线索喂进去。
2. **调用工具**：`inspection_generate_checklist({ storeId, storeName, storeType, note, photoHints, inspectionId })`。
   - 想把结果写回检查单就带 `inspectionId`（会写 `inspections.items` 与 `inspections.reasons`）。
3. **核对返回**：
   - `data.items[]` 每项必须有 `name`、`why`、`weight`（1-5）；
   - `data.reasons` 必须是"为什么查这几项"的一段话，且要引用本次输入里的具体线索；
   - `data.standards` 是本次参考的检查标准（`version` / `source`：客户注入 / 随包交付 / 内置兜底），要能与客户给的标准对上；
   - `data.callId` 是这次模型调用的日志 id（可在 `inspection_model_calls` 里逐条核对）。
4. **失败怎么处理**（三条都不许兜底造清单）：
   - `MODEL_OUTPUT_INVALID` / `MODEL_OUTPUT_EMPTY`：模型输出不合法 → 重试一次；仍失败就如实回报"检查项未生成"；
   - `NO_PROVIDER` / `NO_MODEL` / `MISSING_CREDENTIAL`：模型没配好 → 如实回报并让操作者去客户端模型设置里配；
   - `MODEL_TIMEOUT`：网络慢 → 重试或抬高 `timeoutMs`。
5. **对照检查**（自检，任一条不过就重跑或如实回报）：
   - 换一家门店/换一种业态，检查项集合**应当不同**；如果两次完全一样，说明提示词里混进了固定清单；
   - 每条 `why` 都能对上本次输入里的某个线索；
   - `reasons` 里没有"可能/大概/建议检查"这类没有依据的话。

## 边界与不做什么

- **不做检查项管理后台/编辑器**，不做勾选表（店长端只有非结构化输入）。
- **不把检查项写死成固定清单**；代码里不得出现"生成失败 → 用预设清单"的分支。
- 不判定"这张照片到底有没有问题"（那是照片视觉判断的活）；本技能只管"查哪几项、为什么"。

- 生成动作：插件 `gaia-inspection-core` 的工具 `inspection_generate_checklist`
- 口径出处：`gaia-inspection-core/lib/checklist.js` 的 `CHECKLIST_SYSTEM`（提示词版本 `checklist-v1`）
