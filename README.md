# AI软件赛道 - 门店督导 - 盖亚-门店督导

> ⚠️ **本行格式按《作品提交通知》逐字要求**：「并在Readme文件中第一行改为：赛道名称 - 项目名称 - 队伍名」。
> 项目名称＝订单词「门店督导」，队伍名＝「盖亚-门店督导」。**若需调整项目名称，只改本行与全文一致处。**

「门店督导」是一个**门店巡店自查判断引擎**：门店在交接班时交一张照片 + 一句话，由模型当场决定这一趟该查哪几项、逐项给出判断与依据，并生成整改要求与截止时间；总部督导在另一端复核（通过 / 退回 / 催办），退回后门店回拍，逾期由系统自动催办、超时自动升级。

---

## 一、项目简介

**一句话：为零售连锁餐饮行业的「门店运营 / 督导」部门，解决"督导跑不完所有门店、门店问题留不下可追责记录"的问题。**

| 项 | 内容 |
|---|---|
| 行业 | 零售 · 连锁餐饮 |
| 部门 | 品牌总部的门店运营中心 / 督导部（门店侧角色为店长、店员） |
| 解决什么问题 | ① 督导人力有限，一个月轮不完一圈门店；② 固定检查表填一年，人会闭着眼勾；③ 店长知道督导哪天来，提前收拾；④ 整改要求口头下达，没人跟、三天后恢复原样 |
| 产品形态 | **一个判断引擎，两个入口**——门店端与总部督导端是同一个 Agent 的两个视图，**不是两个 agent** |
| 部署形态 | 本地绿色便携客户端（免安装、只监听本机 127.0.0.1），照片与记录不出本机 |
| 触发点 | 绑定门店本来就有的**交接班**动作——不新增任务，交班时顺手拍一张 |

**产品边界（刻意不做）**：不做考核系统、不做人脸打卡/定位、不做排名、不做账号权限——**上传的监督靠总部现有制度，产品负责把拍来的东西看懂、判断、留证据、追整改**。

## 二、技术栈

### 前端

| 项 | 说明 |
|---|---|
| 运行形态 | 客户端的「client 半」＝**纯浏览器 ESM**（`dsh.client = { platform: "web" }`），由宿主以模块加载，不是独立网页 |
| UI 构造 | **手写 `React.createElement`**（React 18 由宿主提供）——**不引入 UI 组件库、不引入构建工具、无打包步骤** |
| 样式 | **手写 CSS 字符串注入**，令牌集中在 `:root`（圆角 18/12/10/999；间距 4/8/12/16/24/32/40；两级阴影；字号 20/13/11） |
| 图标 | **内联 SVG**（`createElement('svg', …)`，`viewBox 0 0 24 24`、`strokeWidth 1.8`、颜色走 `currentColor`）——**不用 emoji 充当界面图标** |
| 挂载 | 宿主槽位：`sidebar.panellist`（左栏入口「巡店自查」）+ `main`（整屏面板）；`shell.overlay` 仅用于证据挂图浮层 |

### 后端

| 项 | 说明 |
|---|---|
| 运行形态 | 客户端的「宿主半」＝**Node.js ESM**（`"type": "module"`），由宿主进程加载为插件 |
| 插件协议 | 每个包自带 `manifest.json` + `cordis.patch.yml`（声明式挂载补丁），通过槽位与工具注册接入宿主 |
| 数据 | 本地库六张表：`stores` / `inspections` / `findings` / `evidences` / `actions` / `model_calls` |
| 对外接口 | 只读路由 `/api/gaia-inspection/*`（快照 / 证据 / 模型调用日志），**只监听本机** |
| 定时任务 | 进程内**真定时器**扫描逾期（`setInterval`），每次触发把时间戳与结果追加到 `data/logs/scan-log.jsonl`（可核对真实间隔）；「立即扫描」是同一个扫描函数的手动备份入口 |

### AI · 大模型

| 项 | 说明 |
|---|---|
| 模型服务 | 通过宿主 `@deepseek-ai/dsh-llm` 的 provider 抽象调用；**provider 与 model 由宿主的默认模型选择决定**（`agentDefaultModel`），也支持在调用入参里显式指定 |
| 本作品实测形态 | `DeepSeek-V41-Flash`（宿主默认模型），**输入模态 Text + Image** |
| 模态前置校验 | 调图像判断前会调 `llm.resolveModelInfo()` 校验该模型是否声明了 `image` 输入模态；**未声明则不发请求**，返回可诊断错误 `MODEL_NOT_VISION` |
| 凭据 | **代码不读凭据文件、不出现任何 key、不 new 任何 adapter**（`modelroute.js` 注释逐字约束）；Key 由客户端「设置」写入本机 `data/home/.credentials.yaml`，不上传 |

## 三、快速开始

> 本节口径来自随成品交付的《使用说明》（`使用说明.txt`，与产品同源）。

### 环境要求

**无外部依赖。** 运行环境（Node.js / 内核 / 界面）已内置在成品目录内，**不需要另外安装 Node、不需要 npm install、不需要构建**。
支持 Windows x64。

### 安装步骤

1. 把整个成品文件夹复制到任意位置（**建议路径不含中文与空格**）；
2. 双击 `门店督导.exe`；
3. **首次使用在「设置」里填入 API Key**（由你的模型服务商提供；兼容常见接口）。

> 首次在新位置启动偏慢（约 **8~24 秒**，系统对新文件做安全扫描），之后约 **2 秒**。
> 首次运行若出现 SmartScreen「未知发布者」提示：点「更多信息」→「仍要运行」（本程序未做数字签名）。

### 运行方式

| 目标 | 怎么做 |
|---|---|
| 打开 | 双击 `门店督导.exe`；**启动即落在首屏（斜线分屏角色选择）** |
| 进门店端 | 首屏上半块「门店端」，或会话输入区的「门店自查采集入口」 |
| 进督导端 | 首屏下半块「总部督导端」 |
| 换端 | 面板左栏最底部「**切换角色**」→ 回首屏 |
| 回 DSH 会话 | 左栏最底部「**返回会话**」；再进来点左栏「巡店自查」 |
| 看模型调用留痕 | 首屏**中央圆钮**，或任意视图顶栏右「模型调用日志面板」 |
| 退出 | 关窗口只是隐藏到托盘；**真正退出**＝右键托盘图标 →「退出」 |

### 排障

| 现象 | 怎么办 |
|---|---|
| 一直停在「正在启动」 | 看 `data/logs/startup.log`；确认 3082 端口没被占用 |
| 「提交并分析」是灰的 | 三种原因：没选照片 / 说明为空（需 **1–200 字**）/ 该门店刚提交过还在 **60 秒锁**里 |
| 退回后单子从「逾期」里消失 | 正常——退回会把整改截止**重算为「退回时刻 + 8 小时」**并清掉旧逾期/升级标记 |
| 门店端里找不到督导端（反之亦然） | 正常——左栏按定稿**只列本角色项**，换端只能走「切换角色」 |

## 四、核心功能

> 每条都标注落点模块（对应第八节目录结构）。

### 门店端（店长 / 店员）

| # | 功能 | 落点模块 |
|---|---|---|
| 1 | **照片 + 一句话采集**（照片单张、说明 1–200 字、实时字数） | `capture-ui` |
| 2 | **真实提交回执**与五态状态行（待提交 / 正在分析 / 已提交编号 / 分析失败可重试 / 离线排队） | `capture-ui` |
| 3 | **断网降级**：只采集排队、**不产生模型判断**，联网后自动补判 | `capture`（`queue.js`） |
| 4 | **同店重复提交锁**（60 秒；整改回拍不受此限制） | `capture` |
| 5 | **待整改承接面**：退回原因原文 + 共退回几次 + 整改截止 + 「整改后重新提交」 | `capture-ui` |
| 6 | **整改回拍模式**：新单带 `reworkOf` 指向原单，封面显示「整改回拍自 #原单」 | `capture-ui` |

### 判断引擎（核心）

| # | 功能 | 落点模块 |
|---|---|---|
| 7 | **检查项当场动态生成**：按本次照片 + 那句话决定查哪几项，并给出「本次为什么查这几项」的理由列表 | `core/lib/checklist.js` |
| 8 | **客户可注入检查标准**：`standards.json` 支持通用维度 + **按业态专项**，来源区分「客户注入 / 随包交付 / 内置兜底」，改完立刻生效不用重启 | `core`（`standards.example.json` 为示例） |
| 9 | **逐项判断**：判断 / 依据 / 严重度（高·中·低）/ 置信度（高·中·低） | `capture/lib/vision.js` |
| 10 | **证据回指原图**：模型给区域框则画框 + 框心定位点；只给落点则标点；都没有则**不画空框**，只写依据 | `capture` + `oversight-ui` |
| 11 | **模糊照片直说**：材料不可判读时明确回「拍糊了 / 看不清」，**不据此下结论、也不猜** | `capture` |
| 12 | **场景真实性核验**：非经营场景（如居家环境）直接退回「要求重新采集门店真实场景照片」 | `capture`（提示词策略层） |

### 督导端

| # | 功能 | 落点模块 |
|---|---|---|
| 13 | **巡店判断回放看板**：左列表（缩略图/短编号/门店/时刻/状态 chip）+ 右详情 | `oversight-ui` |
| 14 | **四档筛选**（待复核 / 逾期 / 已办结 / 全部）**每档带命中条数**，空档写 0 不隐藏 | `oversight-ui` |
| 15 | **逾期档按责任方两标**：「**待你复核**」（球在督导）vs「**等门店整改**」（球在门店）+ 档顶图例 | `oversight-ui` |
| 16 | **三个动作**：通过 / 退回并说明（**必填原因**）/ 催办；同项不可重复通过 | `action` |
| 17 | **整单状态由规则推导**：全部判断项均通过 → 整单转「已办结」 | `action` |
| 18 | **原单回执四口径**：已回拍 / 还没回拍（剩余多久）/ 已超期（超了多久）/ 没回拍但已办结 | `oversight-ui` |
| 19 | **逾期与升级（自动）**：到整改截止 → 置「逾期」+ 写催办；再过 8 小时 → 置「已升级」+ 写升级动作 | `action` |
| 20 | **动作记录（时间 · 操作者 · 结果）**：自动动作的操作者写「系统」，用 `actorIsHuman` 区分人机来源 | `action` |

### 留痕与演示辅助

| # | 功能 | 落点模块 |
|---|---|---|
| 21 | **模型调用日志面板**：7 列（时间 / 模型 / 提示词版本 / 提交编号 / 请求摘要 / 响应摘要 / 耗时）+ 门店与状态双筛选；**脱敏，不出现 Key / Authorization** | `oversight-ui` + `core/lib/modellog.js` |
| 22 | **演示样例与状态重置**：达标态 / 问题态 / 逾期态 / 看不清态；**重置只清业务表与待判队列，`model_calls` 一行不动** | `demo` |
| 23 | **门店档案（静态只读）**：两家中性示例名门店（快餐档口 / 正餐堂食） | `registry` |
| 24 | **角色视图切换**（演示用，不做账号权限） | `capture-ui` + `oversight-ui` |

### 异常兜底（评分标准点名项）

| 场景 | 兜底行为 |
|---|---|
| 照片模糊 / 材料不可判读 | 明确写「模型只标了『看不清』，没有据此下结论、也没有猜」并给出下一步 |
| 照片不是经营场景 | 场景真实性核验 → 要求重新采集 |
| 某项目标拍不到 | 写「无从判断，本次不列入，待后续采集该区域照片再查」 |
| 模型未给坐标 | 降级为标点 + 依据文字，**绝不画空框** |
| 断网 | 只排队、不出判断，联网补判 |
| 取数失败 / 空态 / 加载中 | 三态齐全（原因 + 重试 / 居中提示 + 下一步 / 骨架屏） |
| 门店不存在 | 结构化空态 `STORE_NOT_FOUND`，不抛异常、不杜撰门店 |

## 五、大模型使用说明

> 本节同时覆盖《交付标准》里两种措辞：「**大模型使用说明**」与「**赞助商API使用清单**」——**调用了哪些模型 / 怎么调 / 是否赞助商提供，三样都写在这里**。

### 5.1 调用了哪些模型

**模型不是硬编码的。** 调用链（`core/lib/modelroute.js`）：

```
入参显式 provider/model
   ↓ 没有则
宿主 llm 服务的默认模型选择（agentDefaultModel）
   ↓ 没有则
返回可诊断错误（NO_PROVIDER / NO_MODEL），不猜、不兜底
```

| 项 | 值 |
|---|---|
| 模型服务来源 | 宿主 `@deepseek-ai/dsh-llm` 的 provider 抽象 |
| **本作品实测使用的 provider / model** | **`api.deepseek.com` 的 `DeepSeek-V41-Flash`**（界面右下角可切换） |
| 输入模态 | **Text + Image**（照片作为图像输入一并送入） |
| 输出模态 | Text（JSON 结构化对象，经 `parseJsonObject` 解析） |
| 是否赞助商提供 | **否——API Key 由使用者自备**（客户端「设置」里填，只存本机 `data/home/.credentials.yaml`） |
| 是否微调 | **不支持微调**，全部靠提示词工程 |

### 5.2 怎么调用（三个调用点 + 两条约束）

| 调用点 | 用途 | 提示词版本字段 |
|---|---|---|
| `inspection_generate_checklist` | 按本次照片与说明，**动态决定本次要查哪几项 + 给出理由** | `promptVersion` |
| 视觉判断（`vision.js`） | 对每项给出：判断 / 依据文字 / 严重度 / 置信度 / 区域框坐标 | `promptVersion` |
| 会话标题（宿主能力） | 宿主自带，非本作品逻辑 | — |

**两条硬约束（写死在代码注释里）**：

1. **凭据不落提示词、不进代码**：`modelroute.js` 首行注释逐字——「不读凭据文件、不出现任何 key、不 new 任何 adapter、不硬编码 provider 之外的凭据」；
2. **调图像前先验模态**：`assertVisionModel()` 校验模型是否声明 `image` 输入；未声明则**不发请求**并返回 `MODEL_NOT_VISION`，避免"假装看见了照片"。

### 5.3 模型调用留痕（`model_calls` 表）

**这是本作品的证据面，评委可当场查验。**

| 字段 | 说明 |
|---|---|
| `id` / `callId` | 调用唯一标识（UUID） |
| `provider` / `model` | 实际使用的服务与模型名 |
| `promptVersion` | **本次调用用的提示词版本**（改提示词必须同步涨版本） |
| `status` | `running` → `ok` / `error` |
| `latencyMs` | 耗时 |
| `usage` | token 用量 |
| `requestSummary` / `responseSummary` | 业务摘要（**脱敏**，不含 Key / Authorization） |
| `tsStart` / `tsEnd` | 起止时间戳 |
| `inspectionId` / `storeId` | 归属的检查单与门店 |

**落库时机（注释逐字）**：「每次模型调用**在调用发生的那一刻**写一条真实记录（`status:'running'` + 开始时间戳），调用结束后再补耗时 / usage / 终态（patch 同一条 callId）；**不许事后批量补写、不许重置清空**」。

**界面入口**：首屏中央圆钮 / 任意视图顶栏右「模型调用日志面板」/ 日志视图左栏项——三处都可进。
