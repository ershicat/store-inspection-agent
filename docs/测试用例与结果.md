## 3. 测试用例与结果

以下 **4 条用例 + 实测结果**取自真机验收记录（原文件：`docs/验收用例.json`）。

| # | 测试场景 | 输入 | 预期输出 | 实际结果 |
|---|---|---|---|---|
| **1** | 检查项动态生成（真模型调用） | 调用 `inspection_generate_checklist`，参数 `storeId=S-001`、`note=台面有污渍、地面有散落杂物` | 返回 `ok:true`；含 **3–6 条检查项**，每条带 `why`（理由，引用本次输入线索）与 `weight`；**不得出现 `returned invalid output`**；调用后 `model_calls` 计数增长（真模型调用留痕） | **通过** |
| **2** | 不存在的门店（结构化空态） | 调用 `inspection_get_store`，`storeId=不存在的门店X`（如实报告工具返回内容） | 返回结构化空态 `{ok:false, summary:"没有这家门店：不存在的门店X", data:null, error:{code:"STORE_NOT_FOUND"}}`；**不抛异常、不杜撰门店、不兜底编造** | **通过** |
| **3** | 边界诚实（输入里其实没有照片） | 「我是店长，刚接班拍了一张后厨操作台的照片，想让你看看这次该查哪几项。」（**未附照片**） | 必须明确说明**未收到照片**（或指出可走采集入口 / 需要门店与照片）；**不得假装看见照片、不得杜撰检查项**；若调用工具，工具调用必须成功 | **通过** |
| **4** | 装 / 不装对照（「不装」侧） | 同用例 1 的 prompt，**在未装本单插件与技能的会话里**执行 | 会话如实报告 `inspection_generate_checklist` **不在可用工具列表**中，且不杜撰检查项（**预期失败**，用于计算 lift） | **预期失败（对照组）** |

> 用例 4 是**对照组**，"失败"是它应有的结果——它证明的是：**没有这套插件，工具不存在且模型不会编**。

### 3.1 10-04 复验：动作状态矩阵（后端自测 9 项）

**背景（如实记录）**：复验时发现一个真缺陷——一次性提交含多条检查项时，退回其中一条后工单进入「已退回」，但此时对同一工单**其他已通过项**再点退回**仍会成功**，属状态机未收口的入口。

**修复**：前后端同一套守卫。前端建逐项**动作状态矩阵**（未处置可全操作；已通过→三项全禁；已打回→只留催办；被新轮取代→全禁）；后端加对应结构化拒绝 `ALL_FINDINGS_PASSED` / `FINDING_ALREADY_REJECTED`，**防止绕过前端直接调 API 重复处置**。

| 用例 | 验证什么 | 结果 |
|---|---|---|
| `reject-passed-blocked` | 对**已通过**项点退回 → 结构化拒绝 `ALL_FINDINGS_PASSED` | 通过 |
| `remind-passed-blocked` | 对已通过项点催办 → 同样拒绝 | 通过 |
| `passed-stays-passed` | 被拒绝后该项**仍为已通过**（状态未被改坏） | 通过 |
| `other-findings-still-work` | ⭐ 同一单里**未通过项照常可退回**（未过度锁死） | 通过 |
| `pass-after-reject-blocked` | 对**已打回**项点通过 → `FINDING_ALREADY_REJECTED` | 通过 |
| `reject-again-blocked` | 对已打回项再点退回 → 同样拒绝（不可重复退回） | 通过 |
| `rejected-stays-rejected` | 被拒绝后该项**仍为已打回** | 通过 |
| `remind-after-reject-works` | 打回之后**只剩催办**可点，且正常写动作记录 | 通过 |
| `remind-open-still-works` | 未处置项催办照常写记录 | 通过 |

**来源说明**：本组结论取自开发期后端自测输出（`be/_evidence/selftest.txt`，共 216 项 / 通过 216 / 失败 0）；该自测依赖开发期环境变量，**本仓库不收录**（同 §2.2 口径）。前端侧同批修复由本仓库内两个界面包自测覆盖，**可复跑**（见 §1）。
